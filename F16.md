# F16: preimage share owner preemption

**Severity:** High. Permanent griefing of Lightning receive on a per-invoice basis. No funds stolen (Lightning HTLC returns to the sender at timeout), but receive for any payment_hash an attacker observes can be disabled with one RPC call and no way back through public APIs.

## The bug

When a Spark user wants to receive Lightning, their wallet shards the invoice preimage via Pedersen VSS and registers the shares against the `payment_hash` on every signing operator. The registration goes through `StorePreimageShareV2`. Three steps in the chain are individually reasonable, and collectively wrong:

1. `lightning_handler.go:149` accepts `user_identity_public_key` from the request body. It doesn't enforce that this matches the authenticated session identity.

2. `preimage_share_flow_handler.go:185` writes the row via `OnConflict(payment_hash).DoNothing()`. The conflict scope is `payment_hash` only. If a row already exists for that hash with a different owner, the upsert silently no-ops and the handler returns nil.

3. `lightning_handler.go:1049` and `:1538` gate `InitiatePreimageSwap` on `preimageShare.OwnerIdentityPubkey.Equals(receiverIdentityPubKey)`. Once the row's owner is wrong, the swap is refused.

Put them together. An attacker who has seen a victim's BOLT11 invoice — the Lightning sender, an LSP, an onion hop, anyone who reads it off a checkout page — calls `StorePreimageShareV2` first, with their own identity in `user_identity_public_key` and a VSS share set they generated for an unrelated random secret. The shares pass `secretsharing.ValidateShare` because they are internally consistent with their own commitments; nothing in the pipeline checks that the share's secret hashes to `payment_hash`. ECIES on the share map doesn't help either; operator pubkeys are public.

The victim's later legitimate registration arrives. The upsert finds the row and silently does nothing. The victim's wallet gets a nil response. When the Lightning sender pays, `InitiatePreimageSwap` runs with `receiver_identity_public_key = victim`, the row's owner is the attacker, and the swap is refused. The HTLC times out, the sender's funds return, and the victim never receives. The row cannot be rewritten through any public API.

## Impact

- Permanent per-invoice. The victim must generate a fresh invoice with a new preimage and hope the attacker doesn't observe that one too.
- One RPC call. No setup, no privileged access, no operator role.
- Reaches every operator. The consensus engine fans the write out; all operators end up with the attacker as owner.
- No fund theft. The Lightning HTLC returns funds at timeout. This is griefing-class, not theft-class.

## Reproduction

Boot the local cluster (`./run-everything.sh` or the `spark/tilt` minikube setup), drop `poc/f16_preimage_share_preemption_test.go` into `spark/so/grpc_test/`, then:

```bash
cd spark
go test -v ./so/grpc_test/ -run TestF16_PreimageShareOwnerPreemption
```

The test sets up two wallets (`victim`, `attacker`), has the attacker call `StorePreimageShareV2` first against the victim's `payment_hash` and invoice with the attacker's identity and an unrelated VSS share, then has the victim call legitimately. Both calls return nil. Querying each operator's stored share via the mock service shows the attacker's bytes on every operator, never the victim's. A passing test is the bug.

## Suggested fix

Two changes; either prevents the exploit, both together are defence in depth.

**1. Reject owner mismatch on conflict.** Replace the silent `DoNothing` in `preimage_share_flow_handler.go:185-196` with an upsert that only updates when the existing row's owner matches the request's owner, followed by a post-insert ownership check that returns `AlreadyExists` on mismatch:

```go
err = tx.PreimageShare.Create().
    SetPaymentHash(req.PaymentHash).
    SetPreimageShare(secretShare.SecretShare).
    SetThreshold(int32(req.Threshold)).
    SetInvoiceString(req.InvoiceString).
    SetOwnerIdentityPubkey(userIdentityPubKey).
    OnConflict(
        sql.ConflictColumns(preimageshare.FieldPaymentHash),
        sql.ResolveWith(func(s *sql.UpdateSet) {
            s.Where(sql.ColumnsEQ(
                preimageshare.FieldOwnerIdentityPubkey,
                sql.Excluded(preimageshare.FieldOwnerIdentityPubkey),
            ))
        }),
    ).
    Exec(ctx)
if err != nil {
    return fmt.Errorf("unable to store preimage share: %w", err)
}

existing, qerr := tx.PreimageShare.Query().
    Where(preimageshare.PaymentHashEQ(req.PaymentHash)).
    Only(ctx)
if qerr != nil {
    return fmt.Errorf("unable to confirm preimage share after upsert: %w", qerr)
}
if !existing.OwnerIdentityPubkey.Equals(userIdentityPubKey) {
    return sparkerrors.AlreadyExistsDuplicateOperation(
        fmt.Errorf("preimage share for payment_hash %x is owned by a different identity",
            req.PaymentHash))
}
return nil
```

Same caller retrying is still a no-op (legitimate consensus retry idempotency). A different caller writing the same payment_hash gets `AlreadyExists`.

**2. Enforce session identity at the gRPC boundary.** In `lightning_handler.go:81` (v1) and the v2 entry at `:149`, call `authz.EnforceSessionIdentityPublicKeyMatches(ctx, h.config, userIdentityPubKey)` before reaching the handler body. An authenticated user can only submit preimage shares under their own session identity.

A regression test that the cross-identity submission is rejected would be worth adding to `spark/so/grpc_test/`; nothing in that directory currently covers this.
